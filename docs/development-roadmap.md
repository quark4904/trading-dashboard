# 개발 로드맵

이 문서는 실제 주문을 안전하게 도입하기 전까지의 개발 순서와 각 단계의 완료 기준을 정의한다.

## 1단계: DCA DRY_RUN 실행 흐름 — 완료 ✅

목표는 활성 DCA 전략을 KST 일정에 따라 평가하고, 실제 주문 없이 플랫폼별 주문 요청을 생성·기록하는 것이다.

- [x] DCA의 매일·매주·매월 실행 일정 지원
- [x] 매주 실행은 요일, 매월 실행은 1~28일을 전략 설정에 저장
- [x] 실행마다 전략 실행 이력과 생성 주문을 SQLite에 저장
- [x] 같은 전략이 같은 예정 시각에 두 번 실행되지 않도록 보장
- [x] 앱 내부 스케줄러와 수동 DRY_RUN 테스트 실행 제공
- [x] 실제 주문 전송을 하지 않는 DRY_RUN 모드 유지

완료 기준: 실행 이력 화면에서 실행 시각, 전략명, 상태, 생성된 DRY_RUN 주문을 확인할 수 있어야 한다. **충족**

제한 사항: 앱이 중지된 동안 지나간 실행 시각은 보정 실행하지 않는다.

## 2단계: DRY_RUN 거래 비용 추정 — 완료 ✅

- [x] 플랫폼·시장별 공식 기본 수수료 정책
- [x] 코드와 분리된 정책 파일 및 실행 시점 재로딩
- [x] 업비트 주문 가능 정보 API의 실제 매수 수수료율 우선 적용
- [x] 전략별 수수료·세금 override와 슬리피지 가정 입력 및 검증
- [x] 금액 주문의 예상 원금·비용·총 소요액 계산
- [x] 수량 주문은 최근 동기화 현재가를 기준으로 계산
- [x] 계산 근거가 없는 수량 주문은 비용 미산출 상태로 명시
- [x] 비용 추정 결과와 적용 요율 출처를 주문 이력과 화면에 저장·표시
- [x] 잔고 동기화 시 최근 실제 체결 이력도 함께 수집
- [x] 업비트 `paid_fee`, 토스 `execution.commission`·`tax` 실제값 우선 저장
- [x] 외부 주문 ID 기반 중복 방지와 실제값·공식 요율 추정값 구분 표시

완료 기준: DRY_RUN 주문에서는 예상 비용과 요율 출처를 확인하고, 실제 체결에서는 API가
제공하는 실제 비용을 우선 확인할 수 있어야 한다. **충족**

제한 사항: 한국투자 주문별 체결 응답에는 주문별 수수료가 없어 공식 요율 추정값으로
표시한다. 기본 체결 조회 기간은 최근 90일이며, 슬리피지와 실제 체결 가격은 DRY_RUN에서
보장하지 않는다.

## 3단계: 주문 전 리스크 검증 — 완료 ✅

- [x] 플랫폼별 주문 가능 현금·최소 주문 금액·거래 시간 확인
- [x] 종목별 주문 가능 여부 및 업비트 주문 가능 정보 사전 조회
- [x] 전략별·일별 예산 한도와 최대 주문 횟수
- [x] 중복 주문 방지용 멱등성 키와 취소 정책

완료 기준: 검증에 실패한 주문은 외부 주문 API를 호출하지 않고 실패 사유를 실행 이력에 남긴다. **충족**

구현 범위: 업비트는 실행 직전 `orders/chance` 응답에서 종목 상태, 금액 주문 지원 여부,
최소·최대 주문 금액, 매수 수수료, 주문 가능 원화를 확인한다. 한국투자·토스는 최근
성공한 잔고 동기화의 통화별 주문 가능 현금과 종목 현재가를 사용하며, 수량 주문의 현재가가
없으면 검증을 거부한다. 국내주식과 미국주식은 각각 정규 거래시간을 확인하고, 전략에는
원화 기준 일일 예산과 일일 최대 주문 횟수를 저장한다.

모든 주문 계획은 외부 호출 전에 검증되며, 실패 시 `risk_rejected` 주문과 실행 이력 오류를
남긴다. 주문에는 36자 이내 멱등성 키와 `reject_before_submission` 취소 정책을 저장한다.
현재 실주문 어댑터가 없으므로 실제 취소 API는 호출하지 않으며, 향후 실주문 전환 시 이
정책을 미체결 주문 취소 규칙의 기본값으로 사용한다.

## 4단계: 운영 안정성 — 완료 ✅

- [x] 외부 API 재시도, 백오프, 호출 제한 대응
- [x] 플랫폼별 동기화·주문 실행 잠금과 장애 알림
- [x] SQLite 백업·복구 및 스키마 마이그레이션 절차
- [x] HTTP API 통합 테스트와 외부 API mock 테스트 확대

완료 기준: 재시작·외부 API 일시 장애·중복 요청 상황에서 자산과 주문 이력이 일관되게 보존된다.
**충족**

구현 범위: 외부 `GET` 호출은 일시적 네트워크·서버 오류와 HTTP 429를 제한적으로 재시도하고,
`Retry-After`와 지수 백오프를 적용한다. 토큰 발급 `POST`는 기본 재시도하지 않는다. 플랫폼별
동기화와 전략 실행은 SQLite lease 잠금으로 직렬화하며, 프로세스가 중단되어도 만료된 잠금은
다시 회수할 수 있다. 동기화·전략·스케줄러 장애와 잠금 경합은 중복을 합친 운영 알림으로
기록하고 API와 동기화 상태 화면에서 확인 처리할 수 있다.

SQLite Online Backup API 기반 백업·복구 CLI와 `schema_migrations` 이력을 제공한다. 백업·복구
명령과 운영 전후 확인 절차는 [`docs/operations.md`](operations.md)에 정리했다.

## 5단계: 접근 보안과 배포 — 미완료 ⏳

- [ ] 대시보드 인증 및 권한 분리
- [ ] HTTPS 리버스 프록시와 외부 접근 제어
- [ ] 비밀값 관리 방식 정리 및 `.env.example` 제공
- [ ] 운영 로그·상태 점검·백업 자동화

완료 기준: 인증되지 않은 사용자가 전략 수정, 동기화, 실행 API를 호출할 수 없다.

## 6단계: 제한된 실주문 전환 — 미완료 ⏳

- [ ] 플랫폼별 주문 어댑터를 별도 승인 플래그 아래 구현
- [ ] 소액·단일 플랫폼·명시적 운영 승인 범위에서만 활성화
- [ ] 앱이 직접 생성한 주문의 접수 결과와 체결·취소 상태 연결
- [ ] 비상 중지와 전체 전략 일괄 중지 제공

완료 기준: 실주문 여부가 명시적으로 통제되고, 모든 주문의 요청·응답·상태 전이를 추적할 수 있다.
