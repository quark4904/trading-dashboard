# 작업 완료 및 배포 운영 규칙

이 문서는 Trading Dashboard의 변경사항을 저장소와 운영 환경에 반영하기로 한 경우의 완료 기준과 순서를 정의한다. 기본 반영 흐름은 **검증 → 커밋 → 푸시 → 배포 → 배포 후 확인**이다.

## 적용 원칙

- 커밋·푸시·배포는 검증이 끝난 뒤 수행하는 별도 반영 단계이며, 작업 요청에 해당 반영 범위가 포함된 경우에만 진행한다.
- 한 커밋에는 하나의 작업 목적만 포함한다.
- API 키, 비밀번호, `.env` 값, 운영 데이터베이스와 같은 민감정보는 커밋하지 않는다.

## 1. 작업 완료 전 검증

변경 범위에 맞는 검증을 실행하고 결과를 확인한다.

```bash
git diff --check
.venv/bin/python -m unittest discover -s tests -v
docker compose config
```

Python 테스트는 시스템 `python3`가 아니라 프로젝트의 `.venv/bin/python`으로 실행한다. `.venv`가 없으면 [`AGENTS.md`](../AGENTS.md)의 생성 절차를 따른다. 코드와 무관한 문서 변경처럼 일부 검증이 적용되지 않는 경우에는 해당 사실을 작업 결과에 기록한다. 검증 명령이 실패하면 원인을 해결하기 전까지 다음 단계로 진행하지 않는다.

문서만 변경한 경우에도 `git diff --check`와 문서 링크·코드 블록의 대상 경로를 확인하고, 프로젝트 설정에 영향을 주지 않았는지 `docker compose config`로 확인한다. 애플리케이션 테스트가 필요하지 않다고 판단한 근거를 작업 결과에 함께 기록한다.

변경사항을 검토할 때 다음도 함께 확인한다.

- `git status`에 의도하지 않은 파일이 없는가
- 비밀값이나 운영 데이터가 스테이징 대상에 포함되지 않았는가
- 기존 기능을 깨뜨릴 수 있는 변경이 있는가
- 데이터베이스 스키마나 환경변수 변경에 별도 조치가 필요한가

## 2. 커밋

검증이 끝나면 의도한 파일만 스테이징하고, 변경 목적을 설명하는 메시지로 커밋한다.

```bash
git status
git add <의도한 파일>
git commit -m "변경 목적을 설명하는 메시지"
```

## 3. 푸시

커밋이 성공하면 현재 브랜치와 연결된 원격 브랜치로 푸시한다.

```bash
git push
```

원격 브랜치가 없거나 인증·네트워크 문제로 푸시할 수 없으면 배포하지 않고 중단 사유를 보고한다.

## 4. 배포

배포 호스트의 프로젝트 디렉터리에서 최신 커밋을 기준으로 Docker Compose 서비스를 재빌드·재기동한다.

```bash
docker compose up -d --build
docker compose ps
curl --fail http://127.0.0.1:8765/api/health
```

배포 전후의 `data/trading_dashboard.db`와 `.env`는 보존한다. 배포 호스트에 접근할 수 없거나 운영 설정이 준비되지 않은 경우에는 배포를 시도하지 말고 해당 상태를 보고한다.

## 5. 배포 후 확인 및 결과 기록

배포가 끝나면 다음을 확인한다.

- 컨테이너가 정상 실행 중인가
- `/api/health`가 성공 응답을 반환하는가
- 시작 로그에 즉시 종료나 설정 오류가 없는가
- 이번 변경과 관련된 화면 또는 API가 정상 동작하는가

작업 결과에는 최소한 다음을 기록한다.

- 실행한 검증과 결과
- 커밋 해시와 메시지
- 푸시한 원격 브랜치
- 배포 여부와 배포 후 상태

## 반영 중단 조건

다음 중 하나라도 해당하면 커밋·푸시·배포를 진행하지 않는다.

- 관련 테스트나 구성 검증이 실패함
- 의도하지 않은 변경 또는 민감정보가 발견됨
- 요구사항이나 변경 범위가 확정되지 않음
- 원격 저장소 인증·네트워크가 준비되지 않음
- 배포 호스트, 운영 설정 또는 필요한 권한에 접근할 수 없음
- 배포 후 health check 또는 관련 기능 확인에 실패함

중단한 경우에는 실패한 단계, 확인된 원인, 재개에 필요한 조치를 함께 보고한다.
